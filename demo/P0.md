# Warden — Hack Brasil 2026 / P0

Warden demonstrates a synthetic organisation's private cryptographic trust under unanimous, three-custodian control. The source is newly authored for this competition. No prior private Royalcrafter code, customer data, real identities or credentials are included.

## Proven local architecture

- Each site generates its own P-256 key and a CSR for one of two fixed, non-public synthetic `*.warden-demo.invalid` names.
- A one-time trusted ceremony creates a private root CA. Its PKCS#8 key is encrypted with AES-256-GCM; the random envelope key is split into three distinct XOR shares. Each custodian has a distinct Ed25519 signing key and a share commitment registered in an independently pinned public manifest.
- Each custodian signs the exact canonical, expiring request digest plus its identity and share commitment. The authority rejects insufficient, duplicate, expired, unrelated or incorrectly signed releases. A transactional signer reconstructs the envelope key only after all three releases pass policy, issues X.509 leaf certificates, renews or signs a CRL, and records public evidence. Completed requests cannot be reused.
- A verifier, with separately pinned root and manifest fingerprints, independently checks the certificate and CRL signatures, three approval signatures, request binding and local audit-chain hashes. Public evidence contains no private shares or signing keys.
- A local dashboard serves a Portuguese judge walkthrough. Its verification button performs two actual TLS connections with hostname/chain verification and compares observed leaf fingerprints to approved records. There is no certificate-warning bypass.

### Security boundary (important)

This is a competition-grade software custody laboratory, **not** a production HSM, certified HSM equivalent, formal threshold-signature/MPC protocol or proof of resistance to a compromised signing host. The envelope key and CA private key must briefly exist in the authorised signing process. A trusted ceremony and secure deletion/release discipline are assumed; Python does not guarantee memory zeroization. Once all three shares are released, a hostile process could copy them or the reconstructed key. The automated local harness invokes independent signing processes with distinct private files, but does not establish physical or OS-account independence. A real deployment must put custodians under separate protected accounts/devices, enforce authenticated transport, and use independently reviewed key-handling or certified hardware where required. Do not serve the authority or custody material publicly. The audit hash chain is not an immutable distributed ledger until independently anchored to an operational Besu network.

## Reproduce local proof

Use Python 3.12+ and install the declared dependency in an isolated environment. From this directory:

```
python -m pip install -r requirements.txt
python -m unittest -v test_warden test_serve_demo test_besu_lab
```

`test_warden` verifies real cryptographic authorisation, denial paths, actual private-CA TLS on loopback, distinct certificate keys, renewal, CRL rejection, durable SQLite records and independent evidence verification. `test_serve_demo` creates a temporary isolated runtime, invokes three separate custodian command processes, tests the actual dashboard/TLS endpoints, and verifies local coordinated stop and restart at an accelerated test threshold. `test_besu_lab` is **offline configuration and verifier logic only**, with explicit mocked RPC fixtures. It does not establish that any Besu node ran.

For the owner-controlled local demonstration, pick a new private runtime directory outside this source tree. It will contain generated demo credentials; do not commit it. Example:

```
python serve_demo.py prepare --runtime ../warden-private-runtime
python serve_demo.py serve --runtime ../warden-private-runtime
```

The dashboard is loopback-only, by default `http://127.0.0.1:8080`. Alpha and Beta serve private TLS on ports 8443 and 8444; the designated verifier validates their synthetic hostnames with the pinned private root, without adding the root to the operating system's trust store. Use the dashboard's TLS verification button and public evidence endpoint. The local supervisor stops all three listeners together after 600 seconds with no genuine activity, avoids counting `/health`, and keeps persistent runtime files intact. Restart with the same `serve` command. This is local process lifecycle evidence, **not** evidence of GCP VM shutdown/restart.

`warden_cli.py` additionally exposes explicit `initialize`, `create-site`, `request`, `approve`, `authorize`, `evidence` and `verify` commands for independent owner-operated custody. Use `--help` on each subcommand. On a shared OS, use ACLs and separate protected custody accounts; POSIX file modes alone are not a Windows access-control boundary. Never use real certificates, production names, or credentials. Retain independent root/manifest pins outside the authority for verifier trust. Generated transfer releases are transient secrets and must never be published.

## Besu next gate (NOT yet operational)

The original integration tool `besu_lab.py` prepares a four-validator QBFT private Docker lab using Besu's own generator and fresh validator keys. It uses a dedicated internal container network, separate persistent node data, four 4 GiB container limits and JSON-RPC bound to designated **loopback host ports only**. No wildcard host allowance, public RPC, production network or known private key is included. An explicit official `hyperledger/besu` release tag or image digest is required; verify the tag before running. Optional `eth-account` is used on the isolated lab host for a newly generated, separately funded audit anchor signer. The public genesis allocation contains only its address and test balance. No external blockchain or real funds.

Official reference: https://docs.besu-eth.org/private-networks/tutorials/qbft . The four-validator configuration was prepared and offline-tested, **not run** in the current environment. After install/approval on an isolated lab host, prepare a separate runtime and start only its compose project, then run `besu_lab.py verify`. The verifier requires all four designated RPC endpoints to agree on chain ID, registered validator set, genesis and a common progressing block. `besu_lab.py anchor` sends only the verified local audit head in an independently signed transaction to the isolated chain and waits for a matching receipt on every validator. Before declaring success, retain the actual receipt evidence. A pending transaction intent is recorded to prevent blind retry after a timeout.
